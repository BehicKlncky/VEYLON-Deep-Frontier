# Working on VEYLON: Deep Frontier

## Project and context

- Java 25, Gradle wrapper, LWJGL 3, OpenGL 3.3, OpenAL and JOML. No game engine; game art and sounds are generated by project code, with bundled shaders and a licensed font.
- Production code: `src/main/java/com/veylon`; headless JUnit tests: `src/test/java/com/veylon`; classpath assets: `src/main/resources`.
- Keep task context small: search for the affected subsystem, then read the relevant sections below. Do not load every design plan, release note or validation record by default.
- Treat source and current build configuration as authoritative for behavior and commands. Historical validation records describe their recorded revision, not a fresh test result.
- Keep repository documentation and commit messages in English; answer the user in their language.

## Invariants

- Keep simulation, world access, meshing, rendering and audio submission on the main thread. Budget expensive work across frames; do not introduce background access to this state.
- Persisted enum ordinals are append-only. Preserve existing save layouts and generator behavior for old worlds; use the save compatibility skill for changes that affect them.
- Seed new simulation/AI random streams from the world seed in `WorldBootstrap` with distinct salts. Presentation randomness must not alter simulation results.
- `World.getBlock` returns `AIR` for unloaded chunks: check loaded columns before using it to decide movement or placement safety.
- Route player damage through the existing damage/affliction entry points so Creative invulnerability remains effective. Check both Creative and Survival when changing their shared behavior.
- Use `Locale.ROOT` for case conversion used in comparisons or identifiers.
- Preserve bounded runtime collections and hot-path allocation limits. See `RuntimeBoundsTest` and the relevant allocation tests when adding per-frame state.

## Validation

Use `.\gradlew.bat` in Windows PowerShell; use `./gradlew` on macOS. JDK 25 is required. Supported release targets are Windows x64, macOS arm64 and macOS x64; build native packages on their target OS/architecture.

| Purpose | Windows command |
| --- | --- |
| Focused test | `.\gradlew.bat test --tests "com.veylon.GameLoopIntegrationTest" --console=plain` (replace the class as needed) |
| Portable verification | `.\gradlew.bat build --console=plain` |
| Performance measurement | `.\gradlew.bat performanceTest --console=plain` |
| Release packaging | `.\gradlew.bat releaseArtifacts --console=plain` |

- The default tests are deterministic and headless; do not initialize GL/OpenAL resources in them. Test production entry points with fixed seeds and isolated mechanics fixtures.
- For code changes, run focused checks while iterating and the portable build before handoff. `build` includes tests and Javadoc/doclint; `releaseArtifacts` already depends on `build`.
- Documentation-only changes need link/path and diff checks, not the game build. Add behavior tests for meaningful changes; avoid tests that merely mirror implementation or prose.
- Wall-clock benchmarks are opt-in and hardware-calibrated. They are not part of the portable build; never relax budgets merely to pass on another machine.
- Rendering changes need the relevant native QA/captures in addition to headless checks. Read the QA section of `docs/DEVELOPING.md` for the actual scene and variables.
- Report the commands actually run, outcomes and unverified parts. Do not reuse historical test counts, screenshots or benchmark numbers as current evidence.

## Git and commit conventions

- Inspect `git status` before editing; preserve unrelated work and stage only task-owned files when committing is requested. Do not commit, tag or publish merely because files were changed.
- Follow the observed English subject format: `type(scope): imperative description`. Common types are `feat`, `fix`, `test`, `docs`, `refactor`, `perf`, `build` and `chore`; choose a concrete subsystem scope.
- Examples from history: `382832d feat(combat): lethal hit zones for projectiles on human targets`; `09c1963 test(save): pin how body fragments survive a save`; `b36bce4 docs(architecture): record body fragments and liquid fire`.
- Release subjects follow `chore(release): prepare vX.Y.Z`; existing release merges use `merge: release vX.Y.Z`. These are message conventions, not instructions to merge or release.
- Keep commits coherent and independently understandable. History often separates behavior, regression coverage, documentation and release preparation; do not force a split that leaves a broken intermediate commit.
- For substantial changes, explain the resulting behavior, why it changed and relevant compatibility/tradeoffs in the body. Add `Validation:` with checks actually performed. Scale body length to the change.
- **Do not add `Co-Authored-By:` / `Co-authored-by:` trailers, AI co-author credits or automatic agent signatures to new commits, including merge commits.** Use the configured Git identity without overriding it.
- This is the user's convention for future commits: older commits reachable through other refs contain co-author trailers, while the inspected HEAD history contains none. Do not copy those trailers or rewrite existing history to remove them.
