# Urban Survival — Decisions

History reconstruction: this record accompanies milestone 02 on `feature/urban-survival`. The dated implementation notes are historical evidence; the split is verified separately.

Decision log, compatibility policy and open owner questions for the roadmap in [DESIGN.md](DESIGN.md). Recorded by milestone 01 on 2026-10-07 against `923345f`. `B-nn` ids refer to verified facts in [VALIDATION.md §2](VALIDATION.md#2-verified-baseline-at-923345f).

**Status vocabulary.**
- **Adopted**: in force. The owner may steer it later.
- **Owner**: a product decision for the owner. The stated default applies until answered.
- **Package NN**: an engineering choice delegated to that package within the stated constraints. The package records its choice here.
- **Superseded**: replaced by a later decision, which is named.

## 2. Compatibility policy


| Id | Rule |
| --- | --- |
| C-1 | Generators 1–3 stay byte-identical. The pins are the gen-1 historical fixture and the gen-3 fingerprints (`WorldGeneratorFingerprintTest`, `HistoricalV020SaveCompatibilityTest`), plus a new absolute gen-2 fingerprint recorded **before** the first refactor. Gen 2 had only a relative pin (B-13). Historical fixtures are never regenerated. **02:** absolute gen-1 and gen-2 terrain fingerprints were recorded at `923345f` from unchanged generator code, before any refactor; the gen-4 placeholder is pinned too. |
| C-2 | Before `GEN_URBAN` exists, tests that mean "the v3 generator" but say `CURRENT_GENERATOR` are retargeted to `GEN_CAVE_IDENTITIES` in the same change. At `923345f` five test files reference `CURRENT_GENERATOR`: `WorldGeneratorFingerprintTest`, `CaveIdentityGenerationTest`, `SaveMigrationTest`, `RuntimeBoundsTest` and `CorruptSaveResilienceTest`. The last one builds an "unsupported future generator" save as `CURRENT_GENERATOR + 1` (`src/test/java/com/veylon/save/CorruptSaveResilienceTest.java:225`); it must become `MAX_SUPPORTED_GENERATOR + 1`, or it would silently test a valid urban save. **02:** the list was re-checked and was complete. All five now name `GEN_CAVE_IDENTITIES` or `MAX_SUPPORTED_GENERATOR`, and the worlds that `SaveMigrationTest` and `CaveIdentityGenerationTest` build through `newWorld` name generator 3 explicitly. No source or document outside this record references `CURRENT_GENERATOR`. |
| C-3 | Feature gates use exact versions or explicit sets, never `>=` (D-02). |
| C-4 | Geometry revisions are frozen per generator version; content revision is per world; retirement only by explicit rejection (D-04). |
| C-5 | New persistent state uses stable `urban.*` section ids in the existing envelope. Each section has its own int version, bounded `readCount`, explicit absent-section defaults and a reader that accepts an explicit version range. An incompatible change gets a new id (the `world.remains` precedent) or a range-accepting reader. The v3 base layout stays frozen. |
| C-6 | Write-side caps must match read-side caps for every urban collection. The legacy crate writer is uncapped against a 100,000 reader cap (B-30); urban data must not repeat that. Respect 256 sections, 16 MiB per section, 128 MiB per file, 100,000 entries per count and 4,000,000 block edits (B-25, B-28). |
| C-7 | Persisted enums are append-only: `BlockType` (1 byte), `ItemType`, `Quest.Type`, `CreatureType`, `BodyFamily`, `Affliction`, `Weather`, `EventType` (B-31). The first package to append to `Weather`, `Affliction` or `EventType` adds it to `SerializedEnumOrderTest`; those three are not pinned today. Urban factions, sites and archetypes use stable string ids. |
| C-8 | Block ids stay within 0–127: `byId` maps negative bytes to `AIR` (B-11). Widening to 0–255 needs a save-compatibility review, an audit of every signed read (chunk, `changedBlocks` codec, layouts, `pendingGen`) and tests. Visual variety uses position-hash or material variants, not new ids (B-73). |
| C-9 | Irreversible facts persist from their first implementation, with tombstones wherever absence is ambiguous. Regeneration, reactivation or load never refills, resurrects or re-rolls. |
| C-10 | A load over a live world is still rehearsed on a throwaway `Game` (B-27). Urban sections must load into that staging game identically. Malformed urban data fails the whole load and never merges partially. |
| C-11 | Every new per-world system gets `reset()` in `WorldBootstrap` plus an assertion in `GameLoopIntegrationTest`. Every new simulation stream is seeded in `reseedSimulation` with a distinct salt (`WorldSeedDeterminismTest` checks this reflectively, B-04). |
| C-12 | The real save slot is never written by tests or QA (D-23). |
| C-13 | **Directions.** (a) New build, legacy save: identical behaviour; no urban state is created. (b) New build, earlier urban revision: the same structures through the frozen version path; the content revision comes from `urban.meta`. (c) Build 0.8.1 or older, urban save: rejected with "unsupported world generator version" before any world replacement (B-26); the live session survives. (d) Older urban-capable build, newer urban save: rejected if the generator version is unknown. New unknown section ids are skipped, and their state is lost on re-save, which the handoff must state. A newer version of a known section fails the whole load (B-28). |

## 5. Change procedure

1. Mandatory owner requirements R1–R10 (DESIGN §1) change only on an explicit owner instruction, recorded here with its date. Difficulty, time or scope pressure is never a reason to drop one; the gate stays pending instead.
2. Adopted decisions change through a new row that supersedes the old one (`Superseded by D-nn`), with the reason and the affected packages and records.
3. Package decisions are filled in by the package that makes them, in the same change as the code. The handoff in PROGRESS.md names them.
4. Any change to persistence, enums or generation also follows `.agents/skills/veylon-save-compatibility/SKILL.md`.
