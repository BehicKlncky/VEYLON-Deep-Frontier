# v0.5.0 engineering validation

Version 0.5.0 is based on `main` at `8dd4451` (v0.4.1). It is a stability and
technical-baseline pass: the three initially scoped High-severity fixes, two
release-review persistence fixes, two measured optimizations, thirty-six new
tests and a structural reduction of the composition root. It
does not change the binary save version, generator version, serialized enum
order or platform baseline.

The analysis that scoped it — including the findings deliberately *not* fixed,
and why — is in
[`v0.5.0-technical-baseline-audit.md`](v0.5.0-technical-baseline-audit.md).

## Scope and behaviour

### Reading untrusted saves

`SaveSystem.load` promised in its own class documentation that an unreadable
save "fails with a clear console message and the game keeps running". Five core
readers broke that promise by using a file-controlled number as an array index
or a list capacity: both weather ordinals, the creature and carcass types, the
event type and `new ArrayList<>(nBlocks)`. The resulting
`ArrayIndexOutOfBoundsException`, `IllegalArgumentException` and
`OutOfMemoryError` are not `IOException`, so none was caught, and all escaped
`Game.run`.

The failure lands after `newWorld` has already released the live world, so a
save half-written during an F5 took the running game with it.

Every dangerous file-controlled value is now validated before use: collection
counts through `readCount`, indexed ordinals and the hotbar through
`readOrdinal`, and player scalars through `readFinite`. Block edits get a
separate, far looser ceiling because
they are the one section a long-lived world can legitimately grow without bound;
the `ArrayList` capacity hint is clamped independently so a hostile length
cannot reserve memory before the first read fails. `load` also catches
`RuntimeException`, so a future unguarded read degrades to a failed load.

### Failure-atomic persistence

The release review found that catching a bad load was not the complete
contract. `save` opened the destination directly, which truncated the last good
file before serialization had succeeded; and an F9 load called `newWorld`
before the late sections had been validated, so returning `false` could leave
the live session replaced by a partial world.

Writes now finish in a sibling temporary file, flush through
`FileChannel.force(true)`, and atomically replace the destination only after the
entire payload succeeds. Loads are capped at 128 MiB and retained as one
immutable payload. When a live world exists, that payload is first loaded into
an isolated `Game`; only a successful validation pass is replayed into the live
instance. Unsupported generator versions are rejected before either pass can
construct a world.

The three AI decision generators were static mutable state. An isolated load
would therefore have perturbed another `Game` even though it never touched that
object graph. Their exact salts and sequences now live on `EntityManager` per
game instance; gameplay output is unchanged, while tests, validators and any
future parallel instance cannot share an RNG cursor.

### Seeded player outcomes

Fourteen gameplay rolls used `Math.random()`. `WorldSeedDeterminismTest`
enumerates `Random` fields reflectively and structurally cannot see a static
call, so the contract established in 0.4.0 was silently incomplete for exactly
the rolls that decide whether the player survives.

`Player` now owns its affliction generator, seeded in its constructor from the
world it belongs to. `PlayerConsumables`, `WorldInteractions`,
`PlayerBlockActions` and `SleepSystem` share `Game`'s lifetime rather than a
world's, so they take the same explicit `setRandomSeed` hook the fifteen
simulation systems already had, salted and called from `reseedSimulation`.

The toxic-fog roll moved from `Game.mediumTick` onto
`Player.tickToxicFogExposure`, beside the other rolls that decide whether the
player gets an affliction.

Because the existing determinism test is reflective, every new field is covered
by it automatically. `PlayerOutcomeDeterminismTest` adds the observable half.

### Projectile ownership

`ProjectileSystem.fire` returns how many projectiles it put in the air, and
`scaleNewestVelocities` adjusts exactly that many from the tail of the live
list. `PlayerCombatSystem.fireBow` previously searched the shared list backwards
for "an arrow", which is correct only while its own arrow is last — and `fire`
adds nothing at the 96-projectile cap.

### Generator and query costs

Two optimizations, both verified bit-identical before their figures were
accepted:

- `ColumnMemo` memoizes `heightAt`, `mountainFactor` and `biomeAt`, which are
  pure functions of seed and column and were recomputed two to four times per
  column per chunk generation.
- `World.getChunk` caches the last resolved chunk. Every block query in the
  engine funnels through it and `chunks` is a `Map<Long, Chunk>`, so each query
  boxed a `Long` before it could hash. The cache cannot go stale: chunks are
  only ever added to the map, and a new world is a new `World`.

`carveCavesDeep` also stops evaluating its second worm-tunnel field eagerly.
That one is kept because it is strictly less work for identical output, not
because it was shown to pay — it measures inside the noise.

### Composition root

`Game` went from 1,496 lines to 886 through five extractions —
`WorldBootstrap`, `AutomatedRunDriver`, `FrontendController`, `HotkeyRouter`,
`PlayerEnvironmentSystem` — each keeping its entry point on `Game` as a
one-line delegate, so native input, the HUD, `EntityManager`, `CrateScreen` and
the gameplay tests are all unaffected. No gameplay rule moved. Five dead fields
orphaned by earlier extractions were removed.

## Compatibility

- Binary saves remain v3, including the original-v3 EOF path and explicit v2
  migration. `SaveMigrationTest` and `HistoricalV020SaveCompatibilityTest` pass
  unchanged.
- World generator version remains 3, and `WorldGeneratorFingerprintTest`
  confirms terrain is bit-identical across three seeds and the legacy generator.
- Persisted enum order is unchanged.
- Java 25, OpenGL 3.3 Core, LWJGL 3.3.6 and the dependency set are unchanged.

The Gradle wrapper now pins the official 9.1.0 binary distribution SHA-256
(`a17ddd85...686c806`). The checked-in wrapper JAR also matches Gradle's
published 9.1.0 checksum, so a substituted build bootstrap or distribution is
rejected before project code executes.

## Test structure

The portable `test` task excludes hardware timing and contains **302
deterministic tests across 61 classes**, up from 266 across 55. The six new
classes:

| Class | Covers |
| --- | --- |
| `CorruptSaveResilienceTest` | corrupt fields fail cleanly; failed writes and live loads preserve the last good state |
| `PlayerOutcomeDeterminismTest` | affliction, poisoning and drop rolls replay from one seed |
| `BowDrawScalingTest` | a short draw slows only its own arrow, including at the projectile cap |
| `WorldGeneratorFingerprintTest` | generated terrain against recorded fingerprints |
| `PlayerEnvironmentSystemTest` | fumarole recognition, POI discovery, camp illness |
| `OrchestratorSizeTest` | `Game` under 1,000 lines, plus budgets on the next-largest classes |

Every targeted test in `CorruptSaveResilienceTest` was verified to fail against
the previous `SaveSystem` and pass against this one, with an intact-save control
that passes against both — so a guard that rejected everything could not have
passed the suite. `PlayerOutcomeDeterminismTest` fails when a single roll is
reverted to `Math.random()`. `BowDrawScalingTest` fails when the backwards
projectile scan is restored.

`performanceTest` contains the five wall-clock benchmarks plus `TickProfileTest`,
a per-system breakdown of a tick. The profile exists because it earned its
place: the release opened by picking two hot spots from reading the code, both
measured inside the noise, and the profile found the real one — chunk-key
boxing — in a single run.

## Performance

Tick/load figures were measured on the reference i7-13850HX, JDK
25.0.1+8-LTS-27, as the best of three runs of the task, each itself the fastest
of seven samples. The durable-save figure was measured in the release-review
pass across five consecutive successful task runs.

| Benchmark | v0.4.1 | v0.5.0 | Change |
| --- | ---: | ---: | ---: |
| chunk tick | 0.431 ms | 0.352 ms | −18% |
| entity tick | 0.434 ms | 0.329 ms | −24% |
| settlement tick | 0.013 ms | 0.010 ms | −23% |
| save | 0.527 ms | 1.481–1.603 ms | durable atomic publication |
| load | 249.5 ms | 180.8 ms | −27.5% |

Attribution, measured by A/B on the same machine state:

| Change | Isolated effect |
| --- | --- |
| generator column memo | load 249.5 → 180.8 ms |
| worm-tunnel short-circuit | load 249.5 → 242.8 ms (inside noise) |
| chunk lookup cache | chunk tick −18%, entity tick −24%, settlement tick −23% |
| plant growth reading its own chunk | plants 0.0638 → 0.0384 ms (below suite resolution) |
| fumarole predicate reorder | inside noise |
| durable atomic save publication | save 0.505 → 1.481–1.603 ms |

Baselines in `docs/PERFORMANCE_BENCHMARKS.md` and the constants in
`PerformanceBenchmarkTest` were changed together. The tick/load budgets were
lowered after measured optimizations; save moved from 0.60 to 1.70 ms because it
now includes a device flush and atomic replacement rather than timing buffered
serialization under the old, weaker durability contract.

## Release gate

- `clean check --rerun-tasks` executed all 302 portable tests across 61 classes
  plus doclint, with zero failures, errors or skips.
- Five consecutive `performanceTest` runs executed all five benchmarks and the
  tick profile against the re-baselined budgets with zero failures.
- `clean releaseArtifacts` completed compilation, another full portable pass,
  fat-JAR creation, `jpackage` and the Windows archive.
- `veylon-0.5.0-windows-x64.zip` is 54,427,086 bytes and contains 354 entries;
  the executable, bundled runtime and launcher configuration are present.
- `veylon-0.5.0-all.jar` is 7,531,608 bytes and records
  `Implementation-Version: 0.5.0` in its manifest.

The pre-release fixed-seed 30-second OpenGL smoke run also passed on the
reference NVIDIA RTX 1000 Ada GPU at 1600x900, VSync off and seed `20260731`:
797.8 average FPS, 1.67 ms p95, 1.93 ms p99, `performanceGate=true`, save/load
complete, all 55 materials, 656 glyphs and 91/91 item icons present,
`glErrors=0`, `khrErrors=0` and `withinHardLimits=true`. KHR debug reported
three medium-severity NVIDIA shader-state recompilation performance messages;
none was an API or shader correctness error, and the smoke gate completed
successfully.

## Known limitations

- Wall-clock baselines remain calibrated for the documented reference machine
  and deliberately run outside portable `test` and packaging jobs.
- The benchmarks measure ticks and serialization, not frames. The fixed-seed
  OpenGL smoke run remains the rendering gate.
- Two known optimizations are deferred rather than done. `World.blockLight`
  costs nine chunk lookups and a `Math.sqrt` per light per cell, for up to
  ~32,000 cells per mesh rebuild; `Renderer.buildDirtyMeshes` allocates and
  fully sorts every frame to pick three chunks. Both are real, and neither can
  be measured here — chunk meshing ends in a GL buffer upload, which the
  headless suite has no context for. They need a mesh benchmark that stops short
  of the upload, which is the natural next piece of this work.
