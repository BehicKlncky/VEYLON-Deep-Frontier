# v0.5.0 technical baseline audit

Version 0.5.0 is based on `main` at `8dd4451` (v0.4.1). This document is the
analysis that scopes the release: what is actually wrong, what is actually slow,
what is actually untested, and what "perfect technical baseline" means in
concrete, checkable terms.

Nothing here is aspirational. Every finding names the file and line that
produces it, and every one of them is either fixed in this release or listed
under [Deferred](#deferred-with-reasons) with the reason it was not.

## Method

- Read every file over 400 lines plus every simulation, combat, save and world
  entry point (46,741 lines of Java across 137 main and 57 test classes).
- Ran the existing gates before touching anything: `test` (266 deterministic
  tests, 55 classes) and `performanceTest` (5 benchmarks).
- Recorded a pre-change measurement on the reference machine so the release can
  prove its own performance claims rather than assert them.

### Pre-change measurement

Reference machine: i7-13850HX, Windows 10 LTSC 19044, JDK 25.0.1+8-LTS-27,
measured 2026-07-31 on `8dd4451`.

| Benchmark | Measured | v0.4.1 baseline | Budget |
| --- | ---: | ---: | ---: |
| chunk tick | 0.388 ms | 0.50 ms | 1.00 ms |
| entity tick | 0.441 ms | 0.55 ms | 1.05 ms |
| settlement tick | 0.015 ms | 0.05 ms | 0.55 ms |
| save | 0.504 ms | 0.60 ms | 1.10 ms |
| load | 259.302 ms | 300 ms | 360 ms |

`load` is 500x the next largest figure and is the only benchmark where the 20%
rule binds rather than the noise floor. It is therefore the only benchmark where
an optimization can be demonstrated rather than argued.

## Severity scale

| | |
| --- | --- |
| **High** | Crashes the process, corrupts or loses player state, or breaks a contract the codebase documents and tests elsewhere. |
| **Medium** | Wrong gameplay outcome in a reachable situation, but recoverable and bounded. |
| **Low** | Off-by-one or waste with no observable gameplay consequence. |

## High-severity findings

### H1 — A corrupt or truncated save crashes the game instead of failing cleanly

`SaveSystem` documents the contract in its own class JavaDoc: a save this build
cannot read "fails with a clear console message and the game keeps running".
The v3 *extension* sections honour that scrupulously — bounded counts through
`readCount`, validated ids, `available() != 0` tail checks. The v3 **core body
does not**:

| Site | Read | Failure on bad input |
| --- | --- | --- |
| `SaveSystem.java:358-359` | `weathers[in.readInt()]` x2 | `ArrayIndexOutOfBoundsException` |
| `SaveSystem.java:404` | `new ArrayList<>(nBlocks)` | `IllegalArgumentException` (negative) or `OutOfMemoryError` (huge) |
| `SaveSystem.java:549` | `types[in.readInt()]` (creature) | `ArrayIndexOutOfBoundsException` |
| `SaveSystem.java:561` | `types[in.readInt()]` (carcass) | `ArrayIndexOutOfBoundsException` |
| `SaveSystem.java:575` | `eventTypes[in.readInt()]` | `ArrayIndexOutOfBoundsException` |

None of those are an `IOException`, so none are caught by the `catch (IOException)`
at `SaveSystem.java:611`. They propagate out of `SaveSystem.load`, through
`Game.completeLoading` or the F9 handler, out of `Game.run` and `Main.main`, and
kill the process.

This is High rather than Medium for two reasons. The blast radius is the whole
process, not the load; and `load` calls `newWorld` **before** it reads any of
this (`SaveSystem.java:349`), so the crash happens after the player's live world
has already been torn down. A half-written save from a power loss during F5 is
enough to trigger it.

**Fix.** Every core count goes through the existing `readCount` bound. Every
enum ordinal goes through one `readOrdinal` helper that throws `IOException`
with the offending value. The outer guard also catches `RuntimeException`, so a
future unvalidated read degrades to "load failed" rather than to a crash.

### H2 — Fourteen gameplay outcomes ignore the world seed

v0.4.0 established the rule and `WorldSeedDeterminismTest` guards it: one seed
must replay identically, whatever ran before it in the same process. The test
reflects over the `Random` field of every system reachable from `Game`. It
cannot see `Math.random()`, and fourteen gameplay-affecting rolls use it:

| File | Outcome |
| --- | --- |
| `Player.java:197,202` | whether a hit starts BLEEDING, and for how long |
| `Player.java:258,261` | whether a fall SPRAINS, and for how long |
| `Player.java:421,423` | whether an unbandaged wound becomes INFECTED, and for how long |
| `PlayerConsumables.java:73,95,108` | food poisoning from meat, its duration, dirty-water poisoning |
| `WorldInteractions.java:388,454` | poisoning from drinking untreated water, bone drop when skinning |
| `PlayerBlockActions.java:197` | whether leaves drop a sapling |
| `SleepSystem.java:156` | whether a miserable night leaves the player SICK |
| `Game.java:1376` | whether toxic fog inflicts SICKNESS |

These are not cosmetic. Bleeding, infection, poisoning and sickness are the
survival layer's whole failure model, and none of them replay. A seeded QA run,
a bug report with a seed, and a regression test that fixes a seed all silently
observe a different game than the one being described.

**Fix.** Each owning system gets a per-world `Random`, salted and seeded from
`Game.reseedSimulation` exactly like the other fifteen; `Player` seeds from the
world it is constructed for. `WorldSeedDeterminismTest` then covers all of them
automatically, because it enumerates `Random` fields reflectively.

### H3 — An under-drawn bow can slow an arrow that is already in flight

`PlayerCombatSystem.fireBow` (`PlayerCombatSystem.java:421-430`) applies the
draw-power velocity scale by searching `projectiles.live` backwards for the
first player arrow and scaling that. It relies on the arrow it just fired being
the last element.

`ProjectileSystem.fire` returns without adding anything when
`live.size() >= MAX_LIVE` (`ProjectileSystem.java:78`). At the cap, the search
finds the newest *previous* arrow instead and multiplies its velocity by up to
0.4 — an arrow the player already released at full draw decelerates in mid-air.
The cap is 96 and a musket fires 8 pellets a shot, so this is reachable in a
firefight, not theoretical.

**Fix.** `ProjectileSystem.fire` returns how many projectiles it actually
spawned, and `fireBow` scales exactly those.

## Medium-severity findings

### M1 — Powder kegs beside fire are armed by two systems with different fuses

`Game.mediumTick` (`Game.java:1383-1391`) walks `fire.burningCells()` and arms
the six cardinal neighbours with a 1.5 s fuse. `FireSystem.mediumTick` already
armed all twenty-six neighbours with `KEG_FUSE_SECONDS` earlier in the same tick
(`Game.java:1357` runs before line 1383), and `tryArmKeg` refuses a keg that
already has a fuse. The `Game` copy is therefore dead: it can never arm a keg,
and its `audio.playFuse` can never fire.

It is not free, though. It allocates a fresh `int[6][3]` table plus a `Vec3i`
per neighbour, for every burning cell, twice a second — 7 arrays and 6 records
per burning cell per tick, up to `MAX_ACTIVE_FIRES` = 220 cells.

**Fix.** Delete it. `FireSystem` is the single owner, which is also what
`docs/ARCHITECTURE.md` says about where fire rules live.

### M2 — `nearestBasaltFumarole` tests its cheapest predicate last

`World.isBasaltFumarole` (`World.java:542-548`) orders its short-circuit chain
air, air-above, sulfur-below, cave-zone. Air is the *most* common state in the
1,331-cell volume `nearestBasaltFumarole` scans every medium tick, and sulfur
underfoot is the rarest. The common case therefore pays three chunk lookups
before rejecting, where one would do.

**Fix.** Test the rare floor block first. Every predicate is pure, so the
reordering is exactly equivalent.

## Low-severity findings (documented, not all fixed)

- **L1 — `(int)` truncation instead of `Math.floor` on world coordinates.**
  `Game.frame`, `Game.slowTick` and `EntityManager.slowTick` cast player
  coordinates with `(int)`, which rounds toward zero and so is wrong by one for
  coordinates in `(-1, 0)`. The consequence is reading a neighbouring column's
  height in a one-block band. Fixed where this release already rewrites the
  line; not chased across the codebase, because it is invisible in play and a
  sweeping change would be unreviewable against the real fixes.
- **L2 — Per-call scratch allocation in `ExplosionSystem`.** The five-ray
  `exposure` jitter table (`ExplosionSystem.java:343`) and the neighbour offset
  table (`:248`) are allocated per entity and per scorch mark. Explosions are
  rare and bounded; noted for whoever next profiles combat.
- **L3 — `Renderer.buildDirtyMeshes` allocates and fully sorts every frame.**
  It builds an `ArrayList`, scans every loaded chunk and sorts, to pick three.
  Real per-frame garbage, but rendering has no benchmark in this suite, so
  changing it here could not be shown to help. See
  [Deferred](#deferred-with-reasons).

## Performance analysis

The three optimizations this release implements were chosen on one rule: each
must move a figure the benchmark suite actually measures, so the claim can be
verified rather than asserted.

### P1 — Short-circuit the second worm-tunnel noise field

`WorldGenerator.carveCavesDeep` (`:274-279`) computes the domain warp, then
tunnel field A, then tunnel field B, then tests `|t1| < 0.065 && |t2| < 0.065`.
The `&&` already short-circuits — but `t2` was computed on the line above, so
every cell pays for it whether or not field A rejected the cell.

Field B is a two-octave 3D fbm: sixteen hashed lattice samples. Field A rejects
the large majority of cells. Moving the `t2` evaluation inside the condition is
bit-identical and removes that work from every rejected cell.

This is the single hottest thing in the codebase. Chunk generation is
~11,500 carved cells per chunk at up to five fbm3 evaluations each, and a load
regenerates 60 chunks from the seed — which is exactly why `load` is 259 ms and
`save` is 0.5 ms.

### P2 — Memoize the per-column terrain queries

`heightAt`, `mountainFactor`, `temperature01` and `moisture01` are pure
functions of `(seed, x, z)`, and they are recomputed two to four times for the
same column within a single chunk generation:

- `generate` calls `heightAt` then `biomeAt`, and `biomeAt` recomputes
  `mountainFactor` and can call `heightAt` again (`:115`);
- `decorate` calls `heightAt` and `biomeAt` again for all 256 columns;
- `decorateCaveIdentities` calls `heightAt` for 144 of them;
- `placePoi` and the POI builders call it again;
- `SettlementPlanner`/`SettlementBuilder` call it from outside the chunk loop.

A small direct-mapped column cache returns the identical `double`/`int`, so the
arithmetic downstream is unchanged. A collision recomputes and is still exact.

### P3 — Cut the medium-tick environmental scan

M1 and M2 together. The dead keg loop stops allocating, and the fumarole scan
stops making two unnecessary chunk lookups for the vast majority of the 1,331
cells it visits, twice a second. Both land in `chunk tick`.

## Test coverage gaps

266 tests is a real suite, and the gaps are not where a coverage tool would
point. They are the places where a contract is stated but nothing checks it.

| # | Missing | Why it is critical |
| --- | --- | --- |
| 1 | Truncated save fails cleanly | H1's contract is written down and untested |
| 2 | Out-of-range weather ordinal fails cleanly | H1 |
| 3 | Out-of-range creature/carcass/event ordinal fails cleanly | H1 |
| 4 | Absurd entry count fails cleanly without allocating | H1 |
| 5 | Player affliction rolls replay from one seed | H2; the existing determinism test structurally cannot see them |
| 6 | Consumable/interaction rolls replay from one seed | H2 |
| 7 | Under-drawn bow scales only its own arrow, at the cap | H3 |
| 8 | Generated terrain matches a recorded fingerprint | Nothing pins generator *output* across code changes — `sameSeedProducesIdenticalDeepChunks` compares two runs of the same build, so P1/P2 could silently reshape every world and it would stay green |
| 9 | Fumarole detection is unchanged by predicate order | P3 |
| 10 | `Game` stays inside its line budget | The 0.4.0 debt work is described in `ARCHITECTURE.md` as a property of the design; nothing stops it regressing |

Gap 8 is the one that matters most. It is written and committed **before** the
generator is touched, following the same characterize-then-change discipline
`EventRollLadderTest` used for the event ladder in 0.4.1.

## `Game.java` size

1,493 lines against a 1,000-line target. `Game` is already orchestration-only
after the 0.4.0 work; what remains is five responsibilities that are separable
without moving a single gameplay rule:

| Extraction | Lines | What moves |
| --- | ---: | --- |
| `WorldBootstrap` | ~200 | `newWorld`, `reseedSimulation`, `setupCamp` |
| `AutomatedRunDriver` | ~140 | `VEYLON_SHOT`/`VEYLON_SMOKE` capture marks, the smoke phase machine and its gate |
| `FrontendController` | ~110 | title/options/loading states, `completeLoading`, `returnToTitle`, graphics apply |
| `PlayerEnvironmentSystem` | ~110 | medium-tick shelter/smoke/fumarole/fog, POI discovery, camp-illness clear, mesh eviction, station scan |
| `HotkeyRouter` | ~80 | `handleGlobalKeys`, `toggle` |

Every public command on `Game` stays a `Game` method, because native input, the
HUD, `EntityManager`, `CrateScreen` and the gameplay tests all reach them
through the `Game` instance — the same trade `ARCHITECTURE.md` already records
for the nine existing collaborators.

## Deferred with reasons

- **`World.blockLight` cost.** It is the hottest query in chunk meshing: nine
  chunk lookups and a `Math.sqrt` per light per cell, for up to ~32,000 cells
  per rebuild, three rebuilds a frame. Replacing the reject test with a squared
  comparison is safe and worthwhile — but `ChunkMesher.buildChunk` uploads to a
  GL buffer, so it cannot be benchmarked in the headless suite, and this release
  does not ship performance claims it cannot measure. It needs a mesh benchmark
  that stops short of `Mesh.upload` first.
- **L3, `Renderer.buildDirtyMeshes`.** Same reason.
- **L1 across the codebase.** Correct but invisible; a 40-site sweep would bury
  the reviewable changes in this release.
- **The nine pre-existing `javadoc` errors.** Present since v0.4.0, none in a
  file this release changes. Fixing them is worth a release of its own.
