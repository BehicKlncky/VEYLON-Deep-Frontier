# v0.4.1 Summary

Stability release prepared on `refactor/v0.4.1-stability`, branched from `main`
at `07e7731` (v0.4.0). Nothing has been pushed; the branch is local and awaits
review.

## Changes Made

### Phase 1: Immediate Fixes

1. **Fixed `attackCooldown` reset behavior** — `PlayerCombatSystem.reset()` now
   clears the melee cooldown alongside the ranged one. Up to 0.45 s of cooldown
   used to survive a world change, so the first swing in a new or loaded world
   could silently do nothing. This is the one deliberate gameplay change in the
   release.

2. **Documented the EventSystem roll ladder** — the cumulative bound structure,
   why season bias shifts the bound rather than the roll, that `else if`
   fall-through is load-bearing, and the camp-illness exception whose victim
   search deliberately sits inside the branch. Each event's precondition and side
   effects are tabulated.

3. **Added beacon endgame integration test** — the three repair stages, their
   resource costs, the Allied trust gate, the victory transition, and a
   half-repaired beacon surviving save/load. `BEACON` and `BEACON_LIT` joined the
   world-state blocks handled by `WorldInteractions.interactWithBlockAt`, so the
   test drives the sequence through production code rather than assigning
   `world.beaconStage`.

### Phase 2: High-Value Improvements

1. **Extracted dormant settlement simulation** — `DormantSettlementSimulation`
   takes the off-screen food, illness, morale and replenishment rules out of
   `SettlementManager` (1521 → 1388 lines), splits the two long methods into
   named pieces, and documents why illness rolls are position-derived rather
   than stream-derived: that is what keeps a settlement's outcome independent of
   simulation order.

2. **Added interfaces for simulation systems** — `SimulationSystem` plus
   `FastTickSystem` / `MediumTickSystem` / `SlowTickSystem`. Three systems had no
   `reset()` because `Game.newWorld` reset them by poking their fields from
   outside; that logic moved onto the systems themselves.

3. **Converted EventSystem to data-driven design** — the 13-branch chain became
   an ordered `EventDefinition` table carrying bound, bias season, precondition
   and effect. Fall-through semantics and the camp-illness exception are
   preserved and now stated in the table itself.

### Phase 3: Maintainability

1. **Reduced Game field visibility** — 13 of 59 public fields became
   package-private, decided by the compiler rather than by reading call sites.
   Ten are UI screen instances; three are debug toggles. Three fields that are
   public purely for out-of-package tests now say so.

2. **Added performance benchmark suite** — tick-cycle, settlement-tick and
   save/load budgets, with baselines in `docs/PERFORMANCE_BENCHMARKS.md`.

## Behavior changes

Two of these commits change observable behavior. Both are intentional and are
called out in their commit messages.

| Change | Effect |
| --- | --- |
| `attackCooldown` cleared on reset | The first melee swing after a world change or load is no longer eaten by the previous world's cooldown. |
| Dormant replenishment RNG | The replenishment timer now draws from the dormant simulation's own salted stream, so for a given world seed the interval sequence differs from 0.4.0. The distribution is unchanged. |

Three smaller ones clear state that previously leaked across worlds, all inside
the `newWorld` contract that `GameLoopIntegrationTest` already asserts:
`TemperatureSystem`'s cached heat sources (block positions in the abandoned
world), and `WeatherSystem`'s `flashTimer` and `lightningStrikes`.

Save compatibility is untouched: v3 saves load, and `SaveMigrationTest` and
`HistoricalV020SaveCompatibilityTest` pass unchanged.

### Verification approach worth noting

The EventSystem conversion was the one change that could silently alter gameplay,
so the characterization test was committed **before** the refactor (`d8902bc`,
then `fb900e2`). Its recorded distribution — 400 rolls across four contrasting
world states — is byte-identical before and after, which is the evidence that the
odds did not move.

## Known limitations

- **The benchmark baselines are single-machine.** They were measured on an
  i7-13850HX under JDK 25.0.1. A flat 20% band is unusable at sub-millisecond
  scale — repeated runs of identical code moved `entity tick` by 27% and
  `settlement tick` by 100% — so the budget is `max(baseline + 20%, baseline +
  0.5 ms)`. Only the `load` benchmark is large enough for the percentage to bind.
  On slower hardware prefer `VEYLON_SKIP_BENCHMARKS=1` over re-baselining
  downward. If these run in CI, expect to re-baseline against the CI machine once.
- **The benchmarks time ticks, not frames.** Rendering needs a GL context the
  test JVM does not have, so a rendering regression will not fail this suite;
  `VEYLON_SMOKE` remains the gate for that.
- **The version has not been bumped.** `build.gradle` still reads `0.4.0`, and
  `CHANGELOG.md` has no 0.4.1 entry. Both are release actions left to the human
  who tags.
- **The event bounds table in the `slowTick` JavaDoc is maintained by hand.** It
  duplicates what `DEFINITIONS` says, and nothing checks the two agree.
